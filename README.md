# HTML Excel Harmonizer

HTML Excel Harmonizer is an internal diagnostic tool distributed as a portable Windows application. It combines faults from an ODIS Engineering HTML report with a DTC reference database and a project-specific Jira history export, presenting the available information together on individual fault cards.

The project was developed to make diagnostic analysis faster: instead of searching several files separately, the user can review the reported fault, its technical documentation and previous investigations in one place.

## Intended use

The application is tailored to a specific internal engineering workflow. It expects the report structure generated by the ODIS Engineering version used in that workflow and the corresponding internal DTC and Jira spreadsheet layouts.

This public repository documents the implementation and automated Windows build process. The application is not a general-purpose reader for arbitrary diagnostic reports or spreadsheets; using it as intended requires the matching internal input files.

## Loading the input files

The application accepts up to three input files:

| Input | Format | Purpose |
| --- | --- | --- |
| Diagnostic report | `.html`, `.htm` | Provides the faults to investigate and their recorded diagnostic data. |
| DTC reference database | `.xlsx`, `.xls` | Adds technical descriptions, notes and diagnostic conditions. |
| Project-specific Jira export | `.xltm` | Adds previous issue records, statuses, fix information and links to Jira. |

The HTML report is required. The DTC reference database and Jira export are optional enrichment sources.

Select the files using the file panels or drag and drop them into the application, then select **Search** to start processing. Progress messages show the current processing stage.

## Building a complete DTC card

### Diagnostic report as the starting point

The application extracts fault records from the consistent HTML report structure. For each recognised record, it creates a card containing the available information:

- DTC code and hexadecimal identifier
- Fault description
- Recorded date and time
- Vehicle odometer reading
- Fault priority
- Malfunction frequency counter
- DTC status

The hexadecimal DTC identifier is the matching key used to find supplementary information in the other files.

### Technical information from the reference database

For each fault, the application looks for the first matching entry in the DTC reference spreadsheet. It adds the available description and diagnostic conditions, including suspension period, troubleshooting or qualification time, error-setting conditions, reset conditions and enable conditions.

A reference description replaces the description displayed on the card when available. A fault without a matching reference entry remains in the results.

### All matching cases from Jira history

The same DTC can appear in multiple issue records within a project. For each fault, the application searches the entire Jira export and attaches all matching entries rather than stopping at the first match.

Each entry can include:

- Issue creation date
- Description
- Current status, including closure or resolution information where present
- Fix information
- A link to the original Jira issue

The status is displayed as supplied in the export. It may contain a closure date, for example `Closed 22.12.22`; this is not a separately calculated closure-date field.

Reviewing the history helps the user recognise known problems, compare earlier occurrences and see whether a resolution already exists. It can also help investigate whether a module with older firmware is exhibiting a previously resolved problem. The application brings the evidence together; the user makes the diagnostic assessment.

## Reviewing and sharing results

The results view presents the combined information on separate DTC cards, with reference data and Jira history alongside the original diagnostic details.

Users can select and hide cards that are not relevant to the current investigation, restore all hidden cards, and export the currently visible results to **PDF**. The export includes the visible fault cards and their available reference and Jira information, and is saved as `analysis-results.pdf`.

Cards with an extracted date are shown first, with odometer availability used as a secondary sorting criterion. This is not chronological sorting. The **Complete data** badge means that both a date and an odometer reading were extracted.

Hiding cards does not modify the source files. File processing, matching and PDF generation are performed within the application. Jira history comes from the supplied export, without a live Jira API connection.

## Portable Windows delivery and CI build automation

The intended internal distribution is a portable **Windows x86-64 executable**. This was chosen to avoid application installation procedures on company equipment and make the tool easy to transfer between Windows workstations. End users do not need to install Node.js, npm or the Rust development toolchain.

The GitHub Actions workflow **Build Harmonizer Windows exe (Tauri)** automates the build and artifact-delivery process:

1. Checks out the repository on a Windows runner.
2. Prepares Node.js and installs the frontend dependencies.
3. Builds the React and TypeScript frontend with Vite.
4. Prepares Rust, the Windows build target and the Tauri CLI.
5. Creates or updates the Tauri desktop configuration.
6. Builds the Windows executable.
7. Uploads the executable as the `harmonizer-exe` workflow artifact.

The workflow is started manually through **Actions → Build Harmonizer Windows exe (Tauri) → Run workflow**. After a successful run, the executable is available in the run's artifacts.

This provides a scripted build process and separates application development from end-user delivery. The workflow builds and uploads the artifact; distribution to internal workstations is handled separately.

## Technologies and implementation

- **React and TypeScript** for the application interface and processing logic
- **Vite** for frontend builds
- **Tailwind CSS and shadcn/ui** for interface components
- **SheetJS (`xlsx`)** for spreadsheet reading
- **jsPDF** for PDF generation
- **Tauri** for Windows desktop packaging
- **GitHub Actions** for automated Windows builds and artifact delivery

The DTC reference parser reads the first worksheet using fixed column positions: **A** for the identifier, **H** for the description, **K/L** for timing information, and **P/Q/R** for diagnostic conditions.

The Jira parser expects a worksheet named `Exporter`, using **A** for creation date, **B** for the issue key, **D** for the description searched for DTC matches, **E** for status and **G** for fix information. Jira matching handles several hexadecimal representations and text-fragment matches, returning all matching rows.

Jira issue links use a workflow-specific base URL defined in `src/utils/jiraDataMatcher.ts`. Report formats, spreadsheet mappings and link configuration must be adapted if the tool is reused in another environment.
